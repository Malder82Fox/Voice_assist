# 11. Как возобновить проект спустя месяцы

Этот документ — самая короткая точка входа для будущего автора или AI-ассистента.

## Шаг 1. Сверить реальность

- [ ] Перечитать README, [Vision](01-VISION.md), [Roadmap](08-ROADMAP.md), [Decisions](10-DECISIONS.md).
- [ ] Проверить актуальную структуру \`main\`, \`master\`, Issues и PR; документация может устареть.
- [ ] Посмотреть на актуальную архитектуру CanLine OS **только при планировании интеграции**.
- [ ] Не переносить в новую ветку виртуальное окружение \`master/env/\` и исторические API-ключи.
- [ ] Проверить, что старые ключи были отозваны; не выводить значения ключей в обсуждения.

## Шаг 2. Подтвердить цель

- [ ] Выбрать один первый пользовательский сценарий с измеримой ценностью.
- [ ] Определить пользователя, ОС, микрофон, локальную сеть, язык и privacy ограничения.
- [ ] Зафиксировать **не цели** — особенно отсутствие управления промышленным оборудованием.
- [ ] Подтвердить фазы, которые пока не нужны, и пересмотреть P0/P1/P2.

## Шаг 3. Подготовить архитектурные решения

- [ ] Сделать короткий ADR по целевой платформе и версиям Python.
- [ ] Согласовать контракт команды, статусы, ошибки и интерфейс skill.
- [ ] Согласовать модель разрешений, подтверждения и аудит до подключения внешних действий.
- [ ] Сравнить STT/TTS альтернативы с актуальными лицензиями и поддержкой русского.
- [ ] При необходимости сделать отдельный CanLine API/spec review с владельцами Core/MES/SCADA.

## Шаг 4. Начать маленькую реализацию

- [ ] Создать Issue VA-CORE-01 (или актуальную замену) и feature branch от текущего \`main\`.
- [ ] Создать минимальный пакет без внешних секретов и без микрофона, покрыть 3 базовые команды тестами.
- [ ] Добавлять голос и плагины отдельно, по одному, со staging/CI и user review.
- [ ] Для CanLine OS начать с mock API и read-only sandbox; не на рабочем PLC.
- [ ] Документировать, что действительно проверено, и обновить decision log.

## Шаг 5. Зафиксировать состояние после сессии

Каждый законченный PR должен обновлять: достигнутые функции, тесты, изменения API, риски, следующий Issue, известные ограничения и дату актуальности документа.

## Быстрый ответ на вопрос «зачем мы всё это начали?»

Чтобы получить универсальный безопасный голосовой интерфейс для личных задач и, в перспективе, для **оперативного чтения данных CanLine OS**: производительность, простои, состояние оборудования, задачи, техническое обслуживание, качество и закупки — без необходимости вручную искать каждый показатель в интерфейсе.

**Это пока идея и документация.** Не считать старый код готовой архитектурой или подтверждённой основой промышленного продукта.
